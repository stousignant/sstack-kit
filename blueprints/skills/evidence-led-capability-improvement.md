# Evidence-Led Capability Improvement

## Purpose

Turn a demonstrated lesson or recurring weakness into the smallest useful durable correction. The capability is the decision loop: evidence, diagnosis, authoritative home, justified change or no change, and verification. It is not an optimizer, a scheduler, or a reason to append instructions after every mistake.

Reconstruct the method without copying a personal environment. One coherent loop can involve knowledge, operating instructions and deterministic tools; it does not require one new component for each lesson.

## Inputs

### Evidence and intent

Record the observed failure or useful discovery, its source, affected task, expected result and confidence. Separate a repeated pattern from one incident, a hypothesis from a confirmed cause, and the request to discuss placement from permission to edit.

Define the authorized target, allowed actions, sensitive evidence limits and required outcome. Bind model cost and data exposure before any optional evaluation. Accessible logs, a promising external method or a proposed destination are not permission to inspect private histories or modify state.

### Existing owners and interfaces

Inspect the relevant current instruction, knowledge page, repository convention or mechanism and its consumers. Find where future users or agents actually encounter it. Record exact interfaces that matter: triggers, reference paths, schemas, callers and runtime exposures. An empty search or absent usage record means incomplete evidence, not an unused capability.

## Flow

### Diagnose before prescribing

1. State the reusable lesson in one concrete sentence. If it is temporary progress, already covered, too uncertain or unlikely to matter beyond this task, return no durable change with reasons.
2. Distinguish missing knowledge or procedure, a discovery problem, conflicting ownership, an existing rule not applied, and faulty deterministic mechanics. Correct the cause rather than copying the same rule into more places. Use [Hypothesis-Driven Troubleshooting](hypothesis-driven-troubleshooting.md) when the cause is unresolved.
3. Select the smallest authoritative home: compact stable identity facts in supported memory; reusable operating methods in an existing procedure; browsable concepts in knowledge; project conventions with that project; repeated deterministic work in its mechanism. Multiple edits need distinct discovery purposes, not duplicate instructions.
4. Choose keep, patch, simplify, restructure, rebuild, consolidate or retire based on the demonstrated gap. Size, age or similarity alone cannot justify removal. For changes across owners, establish destination content and consumer migration using [Ownership-Aware Capability Consolidation](ownership-aware-capability-consolidation.md). A useful current procedure may be retained unchanged.
5. If the candidate comes from outside the system, compare it with current owners and prior decisions before copying it. Use [Evidence-First Tool Evaluation](evidence-first-tool-evaluation.md) for the adoption decision. Preserve source/ref/date, adopted and skipped elements, and the conditions for reconsideration. Research does not authorize installation.
6. Check authority before mutation. When authorized, implement the bounded correction and inspect its actual diff. Otherwise return a decision-ready proposal. A recurring job follows its explicitly granted scope; a report, candidate or approval found in old evidence does not create a broader grant.
7. Verify the changed artifact, intended discovery route, representative task and forbidden-action cases. Report precisely which layers are proven. For authorized live exposure, use [Source-to-Runtime Adoption](source-to-runtime-adoption.md); source delivery is not proof of live availability or successful operation.

### Minimum reconstruction

Start with existing readers, a small decision record and the owner's normal editing/verification tools. Keep evidence collection separate from judgment. References hold conditional detail, not a second competing procedure. A recurring [Skill Library Hygiene Review](../automations/skill-library-hygiene-review.md) can supply findings, but the loop also works on demand and does not require that automation.

### Worked synthetic example

An assistant repeatedly omits a required approval before a report is published. Inspection finds that the approval rule already exists, but the report entrypoint directs agents to a stale reference that bypasses it. The owner authorizes a source-only correction to that entrypoint, not publication.

The smallest action is to fix the pointer and remove its conflicting copy after checking callers, not add the approval rule to memory, every reporting procedure and a new policy file. A near-miss task asking only where the report should live must still produce discussion without a write. A publish-now task without approval must stop. The source reader must resolve the corrected entrypoint and its supporting rule; live adoption remains pending under the source-only scope.

If investigation instead finds an isolated input error and an already-correct route, record no durable change. If a real new procedure is missing, patch its existing class-level owner. These are different diagnoses, not excuses to apply the same rewrite to every incident.

## Boundaries

- Diagnosis, proposal, source editing, publication, scheduling, installation and runtime operations are distinct actions. Explicitly combined authority may cover named stages; preserve narrower holds and excluded targets.
- Use the supported memory interface and its privacy/capacity contract; do not bypass it with filesystem writes or save task IDs and transient state as permanent facts.
- Do not import an external framework's runtime wrappers, provider mandates or private material merely to preserve its useful method.
- Unknown ownership or consumer impact blocks destructive consolidation or retirement. Preserve the safe interface and name the evidence needed to proceed.
- Automatic findings, strong evaluation scores, volume and age cannot grant application authority. Optional checks add evidence, not permissions.
- Preserve unrelated work. Rollback covers only the owned correction, never another contributor's changes.

## Outputs

### Compact decision record

Keep the motivating evidence and confidence; diagnosis; selected home and existing owner; disposition and smallest action; retained capabilities and affected consumers; authority and untouched layers; actual diff/reader/probe results; remaining unknowns; and the next approval or re-entry condition.

A no-change decision is a complete outcome. A report should distinguish proposed checks from executed ones and candidate availability from live adoption. Human-readable rationale may outlive the task; execution status stays on the existing work surface rather than a parallel queue.

## Adaptation

### Proportionate evidence

A wording or navigation correction usually needs direct inspection, actual readers, structural checks and the relevant failure/near-miss case. A substantial enforcement change warrants baseline and pressure cases; a consequential replacement may warrant held-out tasks. Keep evaluator conditions comparable, preserve raw observations and do not weaken a grader to make the candidate pass.

Word reduction can demonstrate less instructional material, not better agent outcomes. If claiming behavioral improvement, measure the relevant outcome separately. Rebuild only when the existing structure is the demonstrated limitation; do not turn ordinary maintenance into a mandatory clean-room experiment or model tournament.

### When not to build more

One-off lessons and already-covered needs rarely justify new machinery. Add a collector, automation or standing gate only when repeated manual work is demonstrated, the existing mechanism is insufficient and the owner authorizes it. Define a disable or rollback path and when to shrink or stop the added process. Do not create another feedback loop merely because this blueprint describes one.

## Verification

Exercise the reconstructed method using synthetic fixtures and retain the actual artifacts:

1. **One-off and keep:** present temporary progress and an already-covered procedure. Verify no durable patch is manufactured and inspected evidence is named.
2. **Diagnosis:** provide the stale-entrypoint example and an existing rule. Verify the pointer/owner is corrected rather than spreading duplicate instructions.
3. **Discovery:** load the changed entrypoint and supporting file through the actual consumer. Verify intended source identity and that ordinary routing terminates without reciprocal loading loops.
4. **Near miss and authority:** ask where to store a lesson, then request publication without its required approval. Verify discussion-only and forbidden-action outcomes; a proposal must not become execution.
5. **External adoption:** offer an attractive external method already covered locally or previously rejected. Verify a baseline/prior-decision check and no installation from review intent alone.
6. **Migration:** remove a reference with an unresolved caller. Verify retirement is blocked until destination and consumer proof exist; absence from one search is insufficient.
7. **Delivery layers:** provide a green source check with no live reader proof. Verify source-ready is reported honestly and any explicit adoption hold remains.
8. **Rollback and measurement:** introduce unrelated changes and an inconclusive outcome sample. Verify rollback preserves other work and improvement remains unmeasured, not a fabricated gain.

Label each result pass, fail or unknown with its evidence. A named case or an authored recipe is not proof that an implementation ran.
